传统LLM读取所有的历史上下文，然后生成一个token，每输出一个token就需要进行一次完整计算。但是投机解码不同。
投机解码使用一个小模型（比如从大模型中提取的几层）生成多个预测token，然后让大模型计算置信度，按照置信度接受多个token，从而实现加速。
原先的token生成显著依赖显存、内存带宽，投机解码可以让一次权重加载生成多个token，从而能有十分显著的速度提升。
从数学上可以证明，投机解码理论上是无损的，不会降低模型输出质量。
前段时间轰动一时的deepseek推理加速技术DSpark就是一种投机解码，它是从MTP的思路上演进而来的。
MTP是一种原生支持投机解码的模型能力，将投机解码能力包括在原模型中，无需独立的外挂模型。

# 12 GB 显存跑 35B MoE：把本地推理从 6 tok/s 调到 60 tok/s 的完整记录

  

> 一台笔记本、一个 35B 的 MoE 模型、一块 12 GB 的独显。

> 这篇文章记录了我把一个"能跑但很慢"的配置，调到"比预期快"的全过程 ——

> 包括三个真正的杠杆、一次把我自己骗了两轮的测量陷阱，以及一份可以直接抄的调优清单。

>

> 所有数字都是同一台机器、同一个后端、同一个测试脚本下测出来的。

> **绝对值不能跨机器迁移，但规律可以。**

## TL;DR

  

如果你只想记三件事：

  

1. **MoE 模型最重要的旋钮，是"把多少层的专家权重强制放在 CPU 上"。**

   这一个参数能让速度差 **7.6 倍**（6.0 → 45.8 tok/s），比其它所有设置加起来都重要。

2. **第二个是 `ubatch-size`（不是 `batch-size`）。** prefill 速率能差 **2 倍以上**，

   直接决定长提示的"首个 token 要等多久"。

3. **投机解码（MTP）能再加 13~30%，但它额外吃显存。**

   如果显存配额不够，它会**同时压垮 prefill 和解码** —— 于是你会得出"投机没用"的错误结论。

   要给它腾地方，而不是关掉它。

  

还有一条方法论，价值可能超过上面三条：

  

> **测 prefill 必须用每轮不同的提示词。**

> 重复用同一个提示会被 KV 前缀缓存命中，你测到的不是 prefill 速率，而是一个垃圾值。

## 1. 先厘清"快慢"的定义：LM Studio 显示的 t/s 是个陷阱

  

事情的开头是一个很常见的困惑：

  

> "我测出来 35.19 t/s，这是快还是慢？为什么同样基模的另一个模型快得多？"

  

要回答这个，先要知道 LM Studio（以及大多数 GUI）显示的那个 t/s 是**怎么算的**：

  

```

显示 t/s  =  生成的 token 数  ÷  (首 token 时间 + 生成耗时)

```

  

分子只有"生成"，但**分母里包含了 prefill** —— 也就是模型把你的整段提示词读完的那段时间。

于是同一个模型，同一个配置，只因为提示词长度不同，这个数字就会剧烈变化：

  

| 提示长度 | 生成的 t/s（纯解码） | 显示 t/s |

|---|---|---|

| ~150 tok | ~46 | **29** |

| ~600 tok | ~44 | **34** |

| ~2500 tok | ~43 | **32** |

| ~10000 tok | ~43 | **20** |

  

**纯解码速度几乎没变，显示值却从 29 掉到 20。**

  

所以那个 35.19 并不意味着"解码慢"，它只是恰好对应"约 600 token 提示 + 200 token 生成"

这个特定形状。这也解释了最初的困惑：**你以为在比解码速度，其实一直在比 prefill 速度。**

  

> **结论**：对比本地模型速度时，**永远先报提示词长度**，否则数字之间没有可比性。

> 想测纯解码，就看引擎日志里的 `eval time`（见附录 B）。

## 3. 杠杆一：MoE 专家放 CPU —— 6.0 → 45.8 tok/s

  

这是最大的一条，也是最反直觉的一条。

  

### 现象

  

模型是 19.9 GiB，显存只有 12 GiB。想全塞进去是不可能的。

但当时的配置把 GPU 卸载比例设成了 100%，也就是 `--n-gpu-layers 999999`。

结果速度**塌到 6 tok/s**，而且 `nvidia-smi` 显示了一个很矛盾的现象：

  

```bash

nvidia-smi --query-gpu=utilization.gpu,utilization.memory --format=csv

# utilization.gpu [%], utilization.memory [%]

# 100 %,             5 %

```

  

**GPU 计算单元 100% 忙，显存带宽却只用了 5%。** —— 忙，但不是在算。

  

### 根因

  

多出来的权重放不进显存，Windows 驱动把它们**兜进了共享内存**（走 PCIe）。

GPU 每个 token 都要从共享内存里把权重捞回来，于是算力全耗在等数据上 ——

`gpuUtil` 拉满，但真正在算的时间很少。

  

引擎日志里其实直接写了：

  

```

common_fit_params: failed to fit params to free device memory:

                   n_gpu_layers already set by user to 999999, abort

```

  

**"用户显式指定了层数，我放弃自动适配"** —— 于是越界无人拦。

  

### 解法：`n-cpu-moe`

  

llama.cpp 有个专门为 MoE 设计的参数 `--n-cpu-moe N`：把 **N 层的专家权重强制放 CPU**，

但**注意力层和 KV 缓存仍然留在 GPU**。

  

为什么这个切法特别对？因为 MoE 的结构天然适合这样劈：

  

- **注意力层**：稠密、每 token 都要用、体积小 → **放 GPU**

- **专家层**：稀疏（256 个里只用 8 个）、体积巨大（占 90%+ 的权重）→ **放 CPU**

  

把它放 CPU 之后，每个 token 只需要从内存里读 **8/256** 的专家 ——

稀疏性被完整保住了，而不是像"全放 GPU"那样每个 token 都要搬 19.9 GiB。

  

> LM Studio 里的对应设置叫 🔤 `Number of layers for which to force MoE weights onto CPU`，

> 是一个 0~1 的比例。（这个名字**没有中文翻译**，界面上就是这行英文。）

  

### 实测曲线（ctx 64000，投机关闭）

  

| 比例 | 实际下发 | 解码 tok/s |

|---|---|---|

| 0 | `--n-cpu-moe 0` | **6.0** |

| 0.30 | ~12 | 12.0 |

| 0.45 | ~19 | 15.1 |

| 0.50 | `--n-cpu-moe 20` | 25.7（**断崖就在这**）|

| 0.585 | `--n-cpu-moe 25` | 44.3 ~ 45.9 |

| 0.70 | `--n-cpu-moe 28` | 45.6 |

| 0.78 | `--n-cpu-moe 32` | 43.5 |

  

**跨度 7.6 倍。** 而且注意断崖：从 20 层到 25 层，速度从 25.7 跳到 44.3。

  

> 这里的"层数"是**专家层数**，不是总层数。比例 × 总层数 ≈ 实际层数，

> 但具体取整规则由软件决定，**永远以引擎日志里的实际值为准**。

## 4. 杠杆二：`ubatch-size` —— prefill 提升 137%

  

搞定了专家分配，解码速度就到位了。但"显示 t/s"仍然不高，因为 **prefill 很慢**。

  

### 先找到正确的旋钮

  

llama.cpp 有两个容易混淆的批处理参数：

  

| 参数 | LM Studio 界面名 | 作用 |

|---|---|---|

| `--batch-size` | 评估批处理大小 | 逻辑批大小，**对速度影响很小** |

| `--ubatch-size` | 🔤 `Physical Batch Size` | **真正驱动 prefill 的那个** |

  

关键规则：**`--batch-size` 只要 ≥ `--ubatch-size` 就行，真正干活的是 ubatch。**

  

### 实测（2500 token 提示，5 轮中位数去掉首轮）

  

| batch / ubatch | prefill tok/s | 首 token 时间 | 解码 tok/s |

|---|---|---|---|

| 2048 / 512（出厂默认）| 610 | 4.23 s | 43 |

| 4096 / 1024 | 842 | — | 43 |

| 8192 / 2048 | 1151 | 2.28 s | 44 |

| **8192 / 4096** | **1355 ~ 1573** | **1.66 s** | **44** |

| 16384 / 8192 | **682** ⚠️ | — | 44 |

  

**prefill 提升 137%，首 token 时间降 60%，而解码速度完全不受影响。**

  

### 长提示下更夸张

  

10000 token 的提示词：

  

| 配置 | prefill | 首 token 时间 |

|---|---|---|

| 2048 / 512 | 620 | **16.15 s** |

| 8192 / 2048 | 1557 | 6.51 s |

| **8192 / 4096** | **1900** | **5.37 s（−67%）** |

  

**光改这一个参数，读一万 token 的时间从 16 秒降到 5.4 秒。**

  

### 但也别贪心

  

表里最后一行是个警告：**ubatch 加到 8192 反而腰斩到 682**。

  

原因不是 CPU 算不过来（我单独测过 `--threads-batch 32`，完全没用），

而是**显存**：更大的 ubatch 需要更大的中间激活缓冲区，

一旦越界，激活被挤进共享内存，prefill 就崩了 —— 但**解码毫发无伤**（还是 44）。

  

> **判据**：如果 prefill 掉到一半而解码不变，就是 ubatch 太大、激活被挤了。

> 往回退一档即可。

## 5. 杠杆三：投机解码 —— 以及它是怎么把我骗了两轮的

  

这一段是整篇文章里我最想讲的，因为它演示了一个非常常见的测量错误。

  

### 背景

  

这个模型是 **MTP 模型** —— 带一个额外训练出来的"多 token 预测"头，

理论上可以做**投机解码**：用小代价的草稿头一次猜几个 token，

再用主模型并行验证，接受的就白赚。

  

### 第一轮：测出 +77%，但那是错的

  

第一版测量显示投机让速度 **+77%**。我很兴奋，但复核发现是**冷启动污染**：

刚加载完模型时第一次请求要付权重页错误、CUDA 上下文初始化等固定成本，

而我恰好把"关投机"跑在冷态、把"开投机"跑在热态。

  

**修正后，5 轮交错复测：45.9（关） vs 47.4（开），差异在噪声内。**

于是我把投机关掉了，并在文档里写下结论：

  

> "投机解码在这台机器上≈零收益，且方差放大 2~7 倍。已统一关闭。"

  

### 第二轮：这个"修正"本身也是错的

  

后来我在做别的对比时，顺手在几个不同配置下又测了一遍投机。结果出现了完全矛盾的现象：

  

| 配置 | prefill | 解码 tok/s | 峰值显存 |

|---|---|---|---|

| 投机**关**，`n-cpu-moe 25` | 1552 | 45.8 | 11305 |

| 投机**开**，`n-cpu-moe 25` | 633 ⚠️ | **32.0** ⚠️ | **11917** ⚠️ |

| 投机**开**，`n-cpu-moe 25`，ubatch 2048 | 621 ⚠️ | **60.1** | 11901 ⚠️ |

| 投机**开**，`n-cpu-moe 28` | 730 ⚠️ | 61.5 | 11919 ⚠️ |

| **投机开，`n-cpu-moe 30`** ✅ | **1746** | **59.1** | 11503 |

| 投机开，`n-cpu-moe 32` | 1704 | 59.0 | 10621 |

  

看出来了吗：

  

**投机的解码速度其实是 59~61，非常有用。** 我第一轮之所以测出"没用"，

是因为**投机需要额外约 600 MiB 显存**（草稿头 + 验证时的额外激活），

而我当时固定用 `n-cpu-moe 25` —— 正好踩着显存悬崖。

  

于是投机一开就**越界**，prefill 从 1552 崩到 633，解码也从 45.8 掉到 32。

**我把"显存不够"误读成了"投机没用"。**

  

而一旦把 `n-cpu-moe` 从 25 抬到 **30**（等于再多让一点权重回 CPU，腾出约 400 MiB），

投机就完全兑现了：

  

| 指标 | 投机关 | **投机开 + moe30** |

|---|---|---|

| prefill | 1552 | **1746** |

| 解码 | 45.8 | **59.1** |

| 首 token 时间 | 1.69 s | 2.32 s |

  

**而且接受率很高** —— 引擎日志实测 **184 个样本，接受率 0.554 ~ 1.000，中位数 0.754**：

  

```

draft acceptance = 0.74457 (  137 accepted /   184 generated), mean len =  3.21

```

  

中位 **75% 的猜中率**，而且 `mean len = 3.21` 说明草稿头每步能产出 3.2 个 token

（正好贴着 `--spec-draft-n-max 3` 的上限）。**这个草稿头是真的准。**

  

### 跨提示长度的最终对比（"显示 t/s"口径）

  

| 提示长度 | 投机关 | **投机开 + moe30** | 增益 |

|---|---|---|---|

| ~250 tok | 34.85 | 37.6 | +8% |

| ~750 tok | 35.88 | **41.7** | **+16%** |

| ~3800 tok | 31.01 | **35.0** | **+13%** |

  

### 教训（这条比结论本身更值钱）

  

> **测一个"额外消耗资源"的特性时，必须先保证资源有富余。**

> 否则你测的不是这个特性，而是资源枯竭。

>

> 我在这上面翻车了两次：第一次是冷启动污染，第二次更隐蔽 ——

> 因为"关掉投机"的对照组跑得很健康，我完全没有怀疑是资源问题，

> 只看到"打开就慢"，就自然而然地归因给了投机本身。

## 6. 那个把所有人骗了的陷阱：KV 前缀缓存

  

在讲方法论之前，必须先讲这个坑，因为它让我**整轮测试全部作废**。

  

### 现象

  

第一版 prefill 测试，我让每个配置重复 5 次同样的提示词。测出来的数字很怪：

  

- 小提示（47 token）的首 token 时间 7.38 s，**比**大提示（267 token）的 2.63 s **还慢**

- 各个配置的 prefill 速率几乎一样，都在 200~270 tok/s

  

### 根因

  

我去看引擎日志，发现里面写着：

  

```

prompt eval time = ... ms / 4 tokens        ← 4 个 token？！

```

  

**每轮只 prefill 了 4 个 token。**

  

因为 llama.cpp 默认开启 **KV 前缀缓存**：如果新请求的提示词和之前某个请求的前缀相同，

它就直接复用缓存好的 KV，**根本不做 prefill**。

  

我 5 轮用同一个提示词 → 第 2~5 轮全是缓存命中 → 我测的是"读缓存的速度"。

  

### 修正

  

**每轮使用不同的随机提示词**，并在发送前记录日志文件偏移、只解析这一段的输出。

  

还有一个次要陷阱：**端到端时间反推速率会把固定开销算进去**。

短提示下这个开销（约 0.8 s，包含首次 token 的调度等）占比极大。

正确做法是**直接读引擎日志里的 `prompt eval time`**，让引擎自己报速率。

## 7. 可复现的测量方法

  

以上所有结论都建立在这套方法上。如果你要自己复测，**请照做**，否则很容易得到假结论。

  

### 7.1 污染源清单

  

| 污染源 | 后果 | 对策 |

|---|---|---|

| **KV 前缀缓存** | 根本没做 prefill，速率是垃圾值 | **每轮用不同的随机提示词** |

| **冷启动** | 首轮慢 40%+，让"关"的组看起来更快 | 先跑 2~3 轮预热，**丢弃第 1 轮** |

| **机器漂移** | 同一配置不同时刻差 **15~30%** | **交错测量**（A/B/B/A），别把 A 全跑完再跑 B |

| **取 e2e 时间反推** | 固定开销被当成 prefill | 读引擎日志里的速率字段 |

| **样本太少** | 单轮结果不可信 | ≥4~5 轮，取**中位数** |

| **日志路径写死** | 跨天后静默读到旧日志 → "数值合理但全是假的" | **自动探测最新的日志文件** |

  

最后一条尤其阴险：我自己的脚本曾经硬编码了一个日期，隔天再跑时

它读的是**两天前的日志**，然后解析出了一些**看起来完全合理**的数字。

如果没有交叉验证，这个错误能一路传播到结论里。

  

### 7.2 推荐流程

  

```

1. 写配置（改 LM Studio 的模型默认配置文件）

2. 卸载所有模型 → 加载目标模型

3. 从 llama-server.exe 的真实命令行回读参数，确认改对了

4. 预热 2~3 轮（短输出）

5. 正式测量：≥4 轮，每轮不同的随机提示词，丢弃第 1 轮

6. 取中位数；关键结论要用 A/B/B/A 交错再测一遍

7. 记录峰值显存

```

  

### 7.3 怎么拿到"地面真相"

  

**不要相信界面显示的参数**。Windows 上可以直接读进程的命令行：

  

```powershell

(Get-CimInstance Win32_Process |

  Where-Object { $_.Name -eq 'llama-server.exe' }).CommandLine

```

  

这一步抓到过好几个问题，包括"我以为改了的参数其实没生效"。

  

> ⚠️ 一个细节：llama.cpp 的参数是**后者覆盖前者**，而某些工具会把

> 用户覆盖项**追加在末尾**。所以读参数时要取**最后一次出现**的值，不是第一次。

## 8. 试过但没用 / 有害的开关（省你时间）

  

这些我都实测过，结论是**别碰**：

  

| 配置 | 结果 | 判定 |

|---|---|---|

| `--threads-batch 32` | 579（不升反降）| CPU 不是 prefill 瓶颈，别调 |

| `gpuStrictVramCap = true` | `--n-gpu-layers 18`，**17.4（−61%）** | 它会粗暴砍卸载层数 |

| 关闭 Unified KV Cache | **18.5（−58%）** | 别关 |

| GPU 卸载比例 0.85 | 35.9 | 别降，保持 100% |

| `numParallelSessions = 1` | 39.6 | 保持默认 |

| `autoFit = true` | 上下文被强行砍到 4096 | 关掉 |

| KV 缓存量化 q4_0 | 解码 49.9，但 **prefill 崩到 194** | q8_0 更平衡 |

| `--threads 32`（默认 24）| 38.5 | 24 是这台机器的甜点 |

| `mlock` / 更少的 checkpoint | 无差别 | 不用管 |

| ubatch 8192 | prefill **682（腰斩）** | 见 §4 |

## 9. "显存快满了"不是危险信号

  

这一节是另一个需要纠正的直觉。我一度以为"离显存上限只剩几百 MiB 很危险，

随便开个浏览器就会崩"。实测之后发现**完全不成立**。

  

我做了两个可逆的挤压实验。

  

### 实验一：吃掉 5 GB 内存

  

用 PowerShell 分配 4.9 GB 并触碰每一页（跑完立即释放）：

  

| 指标 | 无压力 | 5 GB 压力下 |

|---|---|---|

| 空闲物理内存 | 2.07 GB | **0.24 GB** |

| 推理进程工作集 | 16.8 GB | **12.26 GB（被抢走 4.5 GB）** |

| 缺页速率 | — | 8279 次/秒 ≈ **32 MB/s** |

| **纯解码** | 47.5 | **44.2（−7%）** |

| prefill | ~1560 | 1564（几乎没变）|

  

**被抢走了 4.5 GB 内存，只慢了 7%。**

  

原因：模型是用 `mmap` 惰性加载的。被换出的页在需要时按需换回，

而 MoE 每个 token 只碰 8/256 个专家 —— 需要的回读速率（32 MB/s）

跟 NVMe 带宽差着几个数量级。

  

### 实验二：把显存挤到只剩 592 MiB

  

主动往独显上再加载一个 embedding 模型（+209 MiB）：

  

| 状态 | 显存 | 解码 | prefill |

|---|---|---|---|

| 只有大模型 | 11316 / 12227 | 46.1 | 1373 |

| **挤到只剩 592 MiB** | **11635 / 12227** | **48.34** ✅ | **1666** ✅ |

  

**不但没崩，还是那一轮最好的成绩。**

  

### 真正的"悬崖"是什么

  

不是"总量离满有多近"，而是**「每个 token 都要碰的东西被挤出去了」**：

  

| 什么情况 | 被挤的是 | 后果 |

|---|---|---|

| 专家层放 GPU 太多 | 几 GiB **常驻权重** | **6.0 tok/s（−87%）** |

| ubatch 太大 | 大块**中间激活** | prefill −50%，**解码不受影响** |

| 外部抢占 5 GB 内存 | 惰性 mmap 页 | −7% |

| 外部抢占 200 MB 显存 | 几乎没有 | 0% |

  

> **日常只有一条要注意的：别在独显上同时加载第二个大模型。**

> 那才是"每 token 都要碰的权重被挤出去"的真正复刻。

## 10. 附带结论：MTP 版和非 MTP 版留哪个

  

如果你手上同时有这两个版本（同基模，一个有 MTP 头一个没有），**留 MTP 版**。

  

正面对比（两者都钉死同一个 `--n-cpu-moe`，保证专家切分完全一致，

交错六臂、5 轮去首轮、两轮采样）：

  

| 模型 | 解码 tok/s（两次采样）|

|---|---|

| 非 MTP | 45.42 / 46.56 |

| MTP 版，投机关 | 45.81 / 45.52 |

  

**关掉投机时，两者性能完全相同**（差 0.7%，在噪声内）。

  

但非 MTP 版**没有 MTP 头，永远开不了投机** —— 它的天花板就锁在 45.8。

而 MTP 版配合 `moe30` 能跑到 **59**。

  

所以：**MTP 版严格占优，非 MTP 版在任何负载形状上都不占优，只多占磁盘。**

## 11. 换到你的机器上：通用清单

  

具体数值不可迁移，但决策顺序是固定的：

  

**第 1 步：确定"专家放哪"。**

从"全放 GPU"开始，逐步增加 `--n-cpu-moe`，直到速度**跨过断崖**。

判据是引擎日志里的 `common_fit_params` 报错消失，且 `gpuUtil` 不再长期 100%。

MoE 模型这一步的收益远超其它所有设置。

  

**第 2 步：调 ubatch。**

从 512 开始往上加（512 → 1024 → 2048 → 4096 → 8192），

每次看 prefill 速率。**涨到开始掉的那一档就往回退一格**。

prefill 掉一半而解码不变 = 越界了。

  

**第 3 步：如果模型有 MTP/草稿头，开投机，并给它腾显存。**

先在第 1 步的层数上**再加 2~5 层到 CPU**，然后再开投机。

**不要**在踩线状态下测投机 —— 你会得出它没用的错误结论。

  

**第 4 步：其余参数基本不用动。** 见 §8 的负面清单。

  

**第 5 步：用 §7 的方法验证。** 至少交错测两轮。

## 附录 B：怎么读引擎日志

  

这是**最可靠的测量数据来源** —— 让引擎自己报，不要自己拿秒表算。

  

**日志位置**（LM Studio）：

```

C:\Users\<用户名>\.lmstudio\server-logs\<YYYY-MM>\<YYYY-MM-DD>.<n>.log

```

⚠️ **每次读取前先按修改时间取最新的那个文件**，不要写死日期。

  

**要抓的字段**：

  

```

prompt eval time = 1523.45 ms / 2479 tokens (0.61 ms per token, 1627.31 tokens per second)

                  └─ prefill 总耗时      └─ 提示长度                        └─ prefill 速率 ★

  

eval time = 4523.11 ms / 200 tokens (22.62 ms per token, 44.22 tokens per second)

            └─ 解码耗时      └─ 生成数                        └─ 解码速率 ★

  

tg = 43.88 t/s          ← 引擎周期上报的解码速率（另一个参照）

```

  

**投机的接受率**（只在开启投机时出现）：

```

draft acceptance = 0.74457 (  137 accepted /   184 generated), mean len =  3.21

```

`mean len` > 1 才说明投机真的在赚（这里是 3.21，说明每步草稿都能产出 3 个 token）。

接受率中位 0.75；低于 ~0.3 通常就不划算了。

  

**显存越界的证据**：

```

common_fit_params: failed to fit params to free device memory:

                   n_gpu_layers already set by user to 999999, abort

```

看到这个基本可以确定：有东西被迫放进了共享内存。

## 附录 C：LM Studio 里那些藏起来的参数

  

LM Studio 的加载配置面板有个 **「基础 / 高级」分段控件**。

默认在"基础"模式下，**24 个加载参数里只有 2 个可见**

（`contextLength` 和 GPU 卸载比例），其余 22 个都在"高级"里面。

  

**直接生效的配置文件位置**：

```

C:\Users\<用户名>\.lmstudio\.internal\user-concrete-model-default-config\

  <发布者>\<仓库名>\<文件名>.gguf.json

```

（改这个文件比点界面更可靠；改完重新加载模型即可。）

  

**几个实用对照**（中文界面里显示不出来的，就用英文名找）：

  

| 内部键 | 界面显示 | 说明 |

|---|---|---|

| `numCpuExpertLayersRatio` | 🔤 `Number of layers for which to force MoE weights onto CPU` | **第一杠杆**，无中文翻译 |

| `physicalBatchSize` | 🔤 `Physical Batch Size` | **第二杠杆**，无中文翻译 |

| `evalBatchSize` | 评估批处理大小 | 需 ≥ 上一行 |

| `cpuThreadPoolSize` | CPU 线程池大小 | 和 `prediction.cpuThreads` 一起调 |

| `speculativeDecoding.draftMtp` | 投机解码 → MTP | 需配合更大的 `n-cpu-moe` |

  

**一个容易踩的坑**：配置预设（preset）里可能**不包含投机解码这一项**。

于是你切换配置预设时，投机状态会被**静默改动** —— 这是典型的

"我明明没动它，怎么变慢了"的来源。建议在预设里勾上包含投机解码。

## 附录 D：复现脚本骨架

  

把测量自动化的最小骨架（Python，通过 HTTP 调本地 API）：

  

```python

import glob, json, os, random, re, time, urllib.request

  

# 1. 日志文件：永远取最新的，别写死日期

LOGDIR = os.path.expanduser("~/.lmstudio/server-logs")

def newest_log():

    return max(glob.glob(LOGDIR + "/*/*.log"), key=os.path.getmtime)

  

# 2. 提示词：每轮必须不同，否则命中 KV 前缀缓存

WORDS = ["alpha","bravo","cargo","delta","echo","flux","gust","hive"]

def blob(n, seed):

    r = random.Random(seed)

    return " ".join(f"{r.choice(WORDS)}{r.randint(100,99999)}" for _ in range(n))

  

# 3. 只解析本次请求新增的那段日志

def tail(path, prev):

    with open(path, "rb") as f:

        f.seek(prev); return f.read().decode("utf-8", "replace")

  

PP = re.compile(r"prompt eval time\s*=\s*[\d.]+ ms\s*/\s*(\d+) tokens\s*\(([^)]*)\)")

EV = re.compile(r"(?<!t )eval time\s*=\s*[\d.]+ ms\s*/\s*(\d+) tokens\s*\(([^)]*)\)")

RATE = re.compile(r"([\d.]+)\s*tokens per second")

  

def run_once(model, content, max_tokens, log):

    prev = os.path.getsize(log)

    body = json.dumps({"model": model, "max_tokens": max_tokens, "temperature": 0,

                       "stream": True,

                       "messages": [{"role": "user", "content": content}]}).encode()

    req = urllib.request.Request("http://localhost:1234/v1/chat/completions", data=body,

                                 headers={"Content-Type": "application/json"})

    t0 = time.time(); first = None

    for line in urllib.request.urlopen(req, timeout=1200):

        s = line.decode("utf-8", "replace").strip()

        if not s.startswith("data: ") or s[6:] == "[DONE]":

            continue

        try: d = json.loads(s[6:])

        except Exception: continue

        if ((d.get("choices") or [{}])[0].get("delta") or {}).get("content") and first is None:

            first = time.time() - t0                      # 首个 token 时间

    time.sleep(0.4)

    seg = tail(log, prev)

    out = {"ttft": first}

    if m := PP.findall(seg): out["pp_tok"], out["prefill"] = int(m[-1][0]), float(RATE.search(m[-1][1]).group(1))

    if m := EV.findall(seg): out["gen_tok"], out["decode"]  = int(m[-1][0]), float(RATE.search(m[-1][1]).group(1))

    return out

  

def med(xs):

    xs = sorted(x for x in xs if x is not None)

    return xs[len(xs)//2] if xs else None

  

# 4. 主流程：预热 → 多轮 → 丢首轮 → 中位数

def bench(model, units=400, gen=200, reps=5):

    log = newest_log()

    for i in range(3):                                    # 预热，消除冷启动

        run_once(model, blob(units, 9000+i), 8, log)

    rows = [run_once(model, blob(units, int(time.time()*1000)+i*7919), gen, log)

            for i in range(reps)]

    rows = rows[1:]                                       # 丢弃第 1 轮

    return {"prefill": med([r.get("prefill") for r in rows]),

            "decode":  med([r.get("decode")  for r in rows]),

            "ttft":    med([r.get("ttft")    for r in rows])}

```

  

**用法**：写配置 → `lms unload --all` → `lms load <模型>` →

确认命令行参数（见 §7.3）→ `bench(...)`。

关键结论**至少交错跑两轮**（A/B/B/A）。
